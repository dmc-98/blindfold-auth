Blindfold vs Better Auth

Both are open-source, self-hostable Node.js auth libraries. The split comes down to scope: Better Auth covers more frameworks and ecosystem breadth; Blindfold goes deeper on authorization depth, data sovereignty, and operator tooling.

Choose Blindfold when…
  • Your app needs RBAC + ABAC together — roles, attributes, and field-level masking in one policy DSL.
  • You need explainable authorization: trace exactly why a request was allowed, denied, or masked.
  • A tamper-evident, hash-chained audit log is a compliance requirement.
  • Your team wants a Studio UI to write, test, and dry-run policy changes without touching code.
  • You cannot have user data leave your infrastructure under any circumstances.
Choose Better Auth when…
  • You're on a framework Blindfold doesn't support yet (SvelteKit, Remix, Nuxt, Astro, etc.).
  • You need a large plugin ecosystem: Stripe, Expo, Next-specific helpers, etc.
  • Simpler role-based access control is sufficient and you don't need attribute-level policy logic.
  • You want a larger, more active community and frequent minor releases.

Where Blindfold goes deeper

🔍

Explainable authorization

auth.explain({ subject, resource, action }) returns a full trace: which rules evaluated, which applied, which were shadowed, the deciding rule, and any obligations. You can see exactly why a field was masked or a request denied.

Better Auth's authorization is imperative — you write callbacks, not declarative rules, so there's nothing to trace.

🧪

Policy test runner + dry-run

runPolicySuite(cases) runs table-driven allow/deny/mask tests against your live policy set. Failures are self-explaining — you see the actual effect and which rule caused it.

admin.policies.dryRun(proposed) overlays a proposed rule change without persisting it, showing before/after per-case — so you can validate a policy change before shipping it.

🛡️

Hash-chained audit log

Every auth event carries a SHA-256 chain hash linking it to the predecessor. admin.audit.verify() walks the chain; any mutation — a deleted row, a changed field — breaks the chain and reports exactly where.

Useful for SOC 2 / compliance contexts where you need to prove the log has not been tampered with.

🎛️

Studio policy debugger

Run blindfold studio to open a local web UI. The Policy Debugger panel lets you send a test request and read a plain-English narrative of why it was allowed, denied, or masked — without reading JSON. The What-If panel runs your policy dry-run visually. Free; no account required.

🏥

blindfold doctor

blindfold doctor scans your environment for security misconfigurations: missing secrets, low-entropy values, DB TLS disabled, default credentials, Studio exposure on public networks. Criticals exit 1 so they block CI.

🔑

Passkeys-first MFA

Password login gates on a passkey second factor when mfa.passkey.enabled. The client completes the WebAuthn ceremony and receives a session with authStrength: "mfa_passkey". Graceful fallback if no passkey is registered. TOTP is planned as an additional factor.

Coming from Better Auth?

importFromBetterAuth()

Blindfold ships a first-class migration importer so you can move users without a password-reset campaign:

  • Maps name → displayName, emailVerified / image / createdAt / updatedAt → attributes; extra columns pass through.
  • Passwords are not migrated (argon2/bcrypt algorithm mismatch). Use the optional resolvePassword callback to issue temporary plaintext passwords for a grace-period rehash on next login.
  • skipExisting: true makes the import idempotent — safe to re-run.
  • actorId is forwarded to audit events so the migration appears as a single actor in the log.

import { importFromBetterAuth } from '@dmc--98/blindfold-auth'
